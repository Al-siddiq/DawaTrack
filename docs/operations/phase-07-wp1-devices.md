# Phase 7 WP1 — Device/control operations and recovery

WP1 candidate only. No production mutation, migration, main merge or deployment performed by this delivery.

Apply the additive Device migration and deferred Audit FK after Phase6 using approved ordered migration procedure; identify/back up target and rehearse restore in isolation first. Runtime requires registered_devices read/insert/update, existing protected Audit insert/read and sync_changes publication; use a separate migration identity for DDL. Schema readiness fails closed. Do not loosen Audit authority, spoof a verifier, rewrite old migrations or manually edit Device/Audit rows to bypass a partial setup.

Owner: Menu → Shop devices → register this browser with a recognizable name. Use distinct real identities for Staff; installation cookie is not a login. Explicit Check this installation online proves actual cookie roundtrip; status alone does not confer offline trust/readiness. Registered devices list is bounded and Owner-only. Staff can view/check own Device only. Revoke with reason when lost/untrusted; this does not erase transactions. Existing standard-control relevant-set handling arrives in WP2; revocation never silently removes a future pinned obligation.

Proof lost: check saved status and Owner list first. If an active registration matches the browser's safe marker, Owner explicitly recovers it with reason; proof rotates and previous proof stops working. No automatic rotation/retry. A revoked installation cannot be recovered/reactivated; preserve it and explicitly start a new enrollment. Never clear browser/site storage as routine recovery. If marker storage is unavailable/corrupt or references are lost, pause enrollment and have Owner review historical devices/revoke superseded installation before explicit fresh enrollment. Do not copy proof between hosts or expose it in screenshots/logs/support tickets.

Cookie production requirements: HTTPS, host-only __Host-dt_device, Path=/, Secure, HttpOnly, SameSite Strict. Staging is also Secure; only HTTP development uses a nonsecure dt_device cookie. Each platform/custom-domain origin is separately enrolled; migration to another origin requires explicit Owner enrollment and preserves prior origin history. No reverse-proxy header/configuration changes are introduced by this package. Validate actual cookie behavior on the real host.

Rollback: stop Device administration/validation, preserve credential/Audit/Device history and in-flight outcomes, restore complete compatible prior code/assets only after reviewing FK/schema compatibility. Never drop populated Device table/Audit FK or delete evidence. Existing financial writers and controls must retain appropriate safe protection; prefer a reviewed forward fix. No standard reconciliation, PIN, provision, outbox, Device pull/receipt/cursor transport or offline finalization exists here.

Support record: exact commit/inventory, migration status/versions, origin/Shop, user role/grants, public Device UUID, request correlation and sanitized observations. Never include secret/verifier/cookie values or full bodies. Escalate inconsistent proof/scope/Audit/unknown outcomes to Owner and maintainer. Timing/baseline/cutoff locks and relevant-device evidence contracts are in WP1 integration documentation; do not execute WP2 manually as an operational workaround.
