These exactly match the supplied screenshots when the reviewed files are converted from LF to CRLF. Git normalizes text for comparison, so a clean status does not guarantee identical on-disk bytes. Existing files can retain CRLF after checkout rules change. The verifier correctly rejected different physical bytes, but its generic error and original handover did not give an adequate repair path. This is not evidence that the Owner edited the application or needs a Node upgrade.

## Fix

`--check` now reports content/set differences separately from `LINE_ENDINGS_ONLY` differences. Normal checking never writes files. It still compares raw bytes; no newline-insensitive digest or silent approval is introduced.

Explicit `--fix-line-endings` is available **only with --check and a recorded manifest**. Before changing anything, it checks the complete selected file set. It permits a repair only when removing CR from CRLF in valid UTF-8 non-NUL text recovers the exact recorded byte count **and SHA-256**. If any actual content/set difference exists, it aborts without repairing any file. A BOM, changed code, whitespace, missing or added tracked release file still fails. Source/public parity and the complete raw inventory are then checked normally. The manifest is never regenerated by this option.
