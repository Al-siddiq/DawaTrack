# Phase 8 WP3 — Performance and Query-Plan Notes

**Status:** Measurement pending in the Owner's supported MySQL 8.4 LTS environment. No performance result is claimed by source inspection or static tests.  
**Package:** WP3 — Shop Dashboard, Approved Export and Phase 8 Integration.

## 1. Design and bounded request profile

The dashboard composes the four accepted report APIs. It adds no dashboard SQL, N+1 detail lookup, report cache, materialized result, new index or database write.

| Source | Dashboard request | Bounded work |
|---|---|---|
| Sales | `GET /api/v1/shop/reports/sales?group_by=MONTH` plus applied `from`/`to` | Existing WP1 Shop-local range maximum of 366 inclusive days; aggregate series is grouped monthly for the dashboard |
| Stock | `GET /api/v1/shop/reports/stock?state=ALL&page=1&per_page=1` | Existing WP2 aggregate plus one list row; the full Shop summary remains source-owned |
| Customer Debt | `GET /api/v1/shop/reports/customer-debt?status=OWING&customer_status=ALL&page=1&per_page=1` | Existing WP2 Receivable projection and full matching summary; one list row |
| Reconciliation | `GET /api/v1/shop/reports/reconciliation?scope=ALL&page=1&per_page=1` | Existing WP2 finalized evidence summary; one list row |

Only authorized report families are requested. One request per source is in flight at a time. Dashboard refresh is explicit; a Sales period change reloads only Sales. No polling timer or background retry loop is added.

The four source requests execute independently and are not one database transaction. Each card displays its own source `as_of`/`refreshed_at` marker and Shop timezone.

## 2. Request protection

All four report GET paths use the existing `SensitiveRateLimitFilter` with one shared per-signed-in-user bucket of 20 requests per 60 seconds. Exceeding the bucket returns the existing `RATE_LIMITED` 429 response and `Retry-After` header. This does not replace server-side permission checks, Tenant/Shop scoping, or source query bounds.

## 4. Index and cache disposition

No index, migration, SQL twin, materialized summary, cache or invalidation dependency is added in WP3. If measurements show a source query needs an index, do not add it ad hoc. Record the measured need and obtain the required Owner approval; implement the paired CodeIgniter migration, SQL twin, migration register entry, preflight and rollback notes under the repository's existing conventions.

No cache is justified by current measured evidence. All report responses remain `Cache-Control: no-store, private`; the dashboard uses source freshness markers and explicit refresh.
