## Cases P6-01–P6-12

1. **P6-01 — migration.** Apply all migrations in an empty disposable database and apply the new migration to a backed-up populated Phase 5 copy. Compare prior business/Audit/change counts before and after; only the new empty table and migration record are expected. Separately inspect the equivalent [raw MySQL SQL](database/sql/phase-06/20261113100000_financial_movements.sql), applying it only to a separate fresh disposable copy, not again over an applied migration.
2. **P6-02 — native schema.** Use `SHOW CREATE TABLE financial_movements`, `SHOW INDEX FROM financial_movements`, and INFORMATION_SCHEMA foreign-key/check inspection. Compare all 16 columns, signed DECIMAL(19,2), DATETIME(6), UUID collation, INT UNSIGNED Shield actor, all named indexes and same-scope Shop/self FKs with the migration/SQL. Verify actual CHECK expressions and native enforcement; the runtime readiness gate checks structure and named constraint presence, not a complete hash of CHECK definitions. In disposable transactions attempt invalid foreign actors and cross-Shop links, then roll back.
3. **P6-03 — validation.** Preview/post string amounts `1500.00`, `0.01` and maximum `99999999999999999.99`; reject zero, negative magnitude, exponent strings, JSON numbers/floats, three decimals, overflow, blank/overlong explanation and reference, invalid channel, malformed/future/unsupported occurrence times and unknown submitted type/sign/actor/scope/link fields. The server derives SHOP_EXPENSE and negative delta. Use browser developer tools to repeat authenticated same-origin requests with current CSRF/session context; use the normal preview response fingerprint for post. Native SQL CHECKs reject invalid stored type/sign/channel/link/zero rows. DECIMAL storage may coerce or round input before CHECK evaluation: lexical float/exponent/excess-precision rejection is an **API** responsibility, not evidence that SQL can distinguish an already-coerced input.
4. **P6-04 — setup failure.** In separate disposable databases with missing table, wrong column/index or absent named FK/check, history, detail, preview and post must fail explicitly with setup-required 503; no empty-success list or posted movement. Restore via reviewed migration/SQL, not guessed destructive repairs.
5. **P6-05 — Cash expense.** Finalize Starting cash ₦20,000 using the accepted workflow. Open Menu → Money movements → Add expense. Select Cash, enter `1500.00`, explain `Transport for stock delivery`, optionally add a reference/time; review then save once. Verify negative `-1500.00`, Cash, actor, explanation, server saved time and occurrence time in the detail and native rows. One movement, one required FINANCIAL Audit and one financial_movement change must commit. Hand calculation: ₦20,000 − ₦1,500 = ₦18,500. WP1 exposes the single movement's cash effect, **not** the WP4 expected-Cash engine or a live balance tile.
6. **P6-06 — Transfer.** In a fresh Shop with no Starting cash, record Transfer `4000.00`. It saves with `-4000.00` amount delta and `0.00` physical_cash_effect. No cash baseline or physical cash change is inferred from the optional reference.
7. **P6-07 — Cash guards.** Try Cash without finalized Starting cash, then with an active Cash/Full control fixture created through the existing supported control workflow/development fixture procedure. Expect OPENING_CASH_REQUIRED or CASH_CONTROL_ACTIVE and zero new movement/success Audit/change. Transfer remains independent of those Cash guards. Do not invent a public Full Reconciliation UI for this case.
8. **P6-08 — identity and recovery.** Capture an approved command and post twice with the same UUID/content. Only one movement/Audit/change exists; both replies identify it. Repeat with changed amount, channel, explanation, reference or explicit occurrence: conflict, no second evidence. An omitted occurrence remains null in the command and uses saved time when first posted; replay remains valid after clock advancement and guard-state changes. A changed review fingerprint fails before a fresh write. Simulate a lost reply **after commit** in a disposable runtime (pause controller after service returns, before response, then drop connection). Reload: the browser checks the saved UUID by GET. If absent/404, it explains uncertainty and allows explicit re-entry with the **same** UUID; no automatic retry/new-ID expense. A status 404 alone is not proof that a concurrent request cannot commit. Only a UUID is retained in sessionStorage; inspect it for absence of money/explanation/reference. Test a conflicting retry and changing browser user/Shop: no stale financial details leak across namespaces.
9. **P6-09 — isolation.** Repeat history/detail and post tampering between two Tenant/Shop contexts; foreign UUIDs are scoped not found, client actor/scope/type fields rejected, actor derived from session. A Platform Admin without Shop membership cannot operate expenses. No private internal ID, Audit metadata or command hash appears in public DTOs.
10. **P6-10 — authority.** Test Owner; Staff view-only; view+record; record-only; correct/reverse-only; legacy debt.manage; inactive membership; READ_ONLY; BLOCKED/SUSPENDED Shop and CLOSED Tenant. Reads require financial.view; writes additionally financial.record and FULL active access. No automatic Staff grants. Future correct/reverse permissions appear independently in Staff management but have no action endpoints/buttons. Revoke permission between preview and post: backend rejects without evidence.
11. **P6-11 — rollback and locks.** In a disposable checkout/database, inject a temporary exception after insertion, during required Audit and during change publication, one point at a time, inside the owning transaction callback. Confirm all movement/Audit/change rows roll back and generation changes do not commit. Restore files and recheck inventory. With two real database sessions test same UUID, different UUID and Cash-control/permission changes against existing tenant/Shop lock ordering. No duplicate success evidence or partial commit. Do not claim an injected frontend failure proves database rollback.
12. **P6-12 — usable reads and regressions.** Review new/add/review/detail/history on narrow phone and desktop, keyboard-only focus, sheet/modal closing, loading buttons, offline guidance, actionable field errors, empty and failed reads, date/channel filters, paging and browser back/forward. Check existing Sales, Returns, Debt payments/statements, Starting cash, Stock, Owner/Admin/Auth navigation and Staff grant editing remain usable. Brand/icons and bottom-nav count remain unchanged.
